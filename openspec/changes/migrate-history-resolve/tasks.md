## Slice — `migrateResolve` + CLI Wiring (single PR)

Satisfies (spec): `migration-history-resolve` — "MUST require exactly one of `--applied <id>` or `--rolled-back <id>`", "`--applied <id>` … MUST INSERT a row … with `checksum` … MUST NOT execute any statement", "MUST refuse … MUST NOT modify the recorded row" on drift, "`--applied <id>` on an already-recorded, non-drifted migration is idempotent", "`--rolled-back <id>` MUST DELETE the row … MUST succeed as a no-op" when absent, "Resolve refuses unknown migration ids … MUST NOT insert a ledger row", "Resolve touches only the ledger, never `.snapshot.json`". Also closes the `migration-history-integrity` delta scenario "`migrate resolve` cannot be used to silently re-baseline a drifted checksum".

Design ref: Engram #686 — `ResolveOptions extends RunnerSeams` next to `DeployOptions` (`migrate-runner.ts:260`); `migrateResolve` appended after `migrateStatus` (currently ends at line 509); reuses exported `migrationChecksum` (line 117) and `listMigrationDirs` (lines 107-114); id validated by exact membership in `listMigrationDirs(cwd)` **plus** `existsSync(migrations/<id>/migration.sql)` — this is the path-traversal hardening; flag validation happens inside `migrateResolve` before `createClient` is invoked; `DELETE ... RETURNING name` for the rolled-back path; no `BEGIN`/`COMMIT`, no `pg_try_advisory_lock`; CLI wiring in `index.ts` after the `status` block (`migrate.command("resolve")` with `--applied <id>`/`--rolled-back <id>`).
